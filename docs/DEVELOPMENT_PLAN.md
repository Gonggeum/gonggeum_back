# 백엔드 개발 순서

작성일: 2026-10-07 · 기준: 기능명세 v3.3 / ERD v1.3 / API v1.0

## 현재 위치

기초 프로젝트와 개발용 MySQL·Redis 환경은 준비되어 있다. 이전 실행 검증에서 빌드·테스트 5개와 실제 DB·Redis readiness `UP`을 확인했다. V1/V2로 인증·파일 참조·공통 기록 기반 테이블 14개를 적용했다. A01 약관 조회와 A02 중복 확인을 구현했고, 기본/단위 10개와 MySQL·Redis 통합 12개 시험이 통과했다. 가입·로그인·JWT·팀/프로젝트 API는 아직 구현하지 않았다. Security는 상태 확인 및 A01/A02만 공개한다.

따라서 다음 작업은 **A03 회원가입의 원자 저장과 자동 로그인·세션 인증 구현**이다. 0~1단계 전체가 완료된 것은 아니며 프런트 인증 배치 합의, 감사/업무 사건 저장, 멱등 실행 서비스 등은 해당 쓰기 기능 전에 남아 있다. 상세 완료 범위는 [작업 보고서](reports/2026-10-07-auth-foundation.txt)를 참고한다. 이 문서는 구현 계획이며 아래 미완료 항목이 이미 개발됐다는 뜻이 아니다. 작업 기간은 인원과 가용 시간이 정해진 뒤 산정한다.

## 기준 문서와 우선순위

- [기능명세 v3.3](requirements/공금이_웹앱_기능명세서_v3.3.md): 업무 정책의 우선 기준.
- [ERD 테이블 명세 v1.3](erd/공금이_ERD_테이블_명세서_v1.3.md), [전체도](erd/공금이_ERD_전체도_v1.3.png): 36개 테이블과 무결성 규칙.
- [API 명세 v1.0](api/공금이_API_명세서_v1.0.md), [OpenAPI](api/공금이_OpenAPI_v1.0.json): 97개 경로·111개 HTTP 작업의 계약.

P0/P1/P2는 원문 기능 우선순위이고, 아래 단계 번호는 의존관계를 고려한 권장 구현 순서다. P0 데이터 기록을 P1 조회 화면 개발까지 미루지 않는다. API 문서의 ‘설계 제안’은 팀과 합의할 대상이며 자동으로 확정 정책이 되지 않는다.

## 1. 스키마와 공통 저장 기반

ERD §11.1을 따른다. **테이블 → PK/UK → 일반·복합 FK → CHECK** 순으로 만들고, `users`와 `stored_files`의 순환 참조는 양쪽 테이블 생성 후 FK를 추가한다. 테이블 생성 순서와 API 구현 순서는 별개다.

- [ ] 계정·약관·동의·세션·인증 자격·보안 설정·로그인 이력·알림 기본값 테이블을 준비한다.
- [ ] 연관 파일 메타데이터 등 선행 FK 대상도 함께 준비한다. 단계별 DDL을 나눌 경우 해당 기능 공개 전 필요한 제약을 모두 연결한다.
- [ ] `audit_logs`, `idempotency_requests`와 업무 사건/알림 저장 기반을 첫 쓰기 기능부터 사용할 수 있게 준비한다.
- [ ] 파일 임시 정리에도 필요한 `deletion_jobs`, `deletion_job_items`를 P0에 준비한다. 팀 전체 삭제 API는 P1에 연다.
- [ ] 명세의 ID 문자열, 단건 금액 정수, 합계 문자열, nullable PATCH의 ‘생략/명시 null’ 구분을 DTO에 반영한다.
- [ ] 공통 권한 확인, 명세 오류 코드, 멱등 키/요청 해시, 감사 기록, version 충돌, 트랜잭션 경계를 정의한다.
- [ ] 서버 UTC와 회계 날짜 Asia/Seoul을 구분하고 테스트용 Clock을 사용한다.

완료 기준: 적용된 DDL을 Hibernate validate 및 MySQL 제약 시험으로 확인한다. `ddl-auto=update`로 구조를 우회하지 않는다. 감사/멱등 저장은 필요한 업무와 동일 트랜잭션에 참여한다.

## 2. 계정·인증 — 첫 번째 기능 단위

대상: **A01~A04, A06~A07, S01**. A04의 2FA 분기는 9단계다.

- [ ] 약관 조회 → 중복 확인 → 가입을 구현한다. 사용자·약관 동의·필수 기본 설정을 원자 생성한다.
- [ ] 비밀번호 해시, 로그인 실패 횟수·잠금, 로그인 이력을 구현한다.
- [ ] access 2시간 / refresh 14일과 DB 세션 sid를 구현한다. 모든 보호 요청에서 서명/만료와 현재 sid 활성 상태를 검증한다.
- [ ] refresh 회전은 14일 절대 세션 만료를 연장하지 않도록 구현하고 동시 갱신 정책을 합의한다.
- [ ] refresh 쿠키 Secure/HttpOnly/SameSite/Path, CSRF 토큰과 Origin 검증을 연결한다. 로컬 HTTPS 또는 개발 프록시 전략도 정한다.
- [ ] 로그아웃·세션 회수 후 이미 발급된 access도 차단한다. reset/challenge/reauth 자격을 업무 access로 허용하지 않는다.
- [ ] SecurityConfig의 공개 경로를 필요한 API에만 열고 보호 경로에 인증 필터를 연결한다.

완료 기준: 가입 → 로그인 → `/me` → 갱신 → 로그아웃의 정상 흐름, 만료·재사용·오류 목적 토큰·CSRF 실패·회수 세션 거절을 시험한다.

## 3. 팀·초대·역할

대상: **T01~T03, T05~T07, I01~I08**.

- [ ] 팀 생성 시 OWNER와 활성 멤버십을 함께 저장한다.
- [ ] 팀 목록·상세·팀원 조회와 역할 변경/OWNER 위임을 구현한다.
- [ ] 초대 생성·재발송·취소·확인·수락/거절을 구현하고 만료·단일 소모를 보장한다.
- [ ] 초대 수락 동시 요청이 활성 멤버십을 중복 생성하지 않도록 시험한다.
- [ ] CSV 미리보기/선택행 확정과 부분 성공 결과를 구현한다. I07/I08도 명세상 P0다.
- [ ] 팀 운영 감사와 초대/역할 변경 알림 사건을 저장한다. 알림 UI가 없어도 기록은 빠뜨리지 않는다.
- [ ] 미가입 이메일 발송은 별도 outbox/큐 설계를 합의한다. `notification_deliveries`의 NOT NULL 수신자에 가짜 user_id를 넣지 않는다.

완료 기준: 사용자 A가 팀을 만들고 B를 초대해 명시 수락으로 참여할 수 있다. 역할별 거절, 소유권 원자 위임, 초대 동시 소모를 검증한다. 팀 탈퇴·추방은 후임 총무 보호가 완성되는 10단계까지 공개하지 않는다.

## 4. 프로젝트·참여자·기본 카테고리

대상: **P01, P02, P05, P07(읽기), C01**.

- [ ] 프로젝트 생성·참여 멤버십·총무·기본 카테고리·예산 기본 상태를 원자 생성한다.
- [ ] 신규 `target_budget=NULL`을 유지한다. 미설정과 0원을 구분한다.
- [ ] 팀 OWNER/ADMIN/MEMBER와 PROJECT_ADMIN/PROJECT_MEMBER를 분리한다.
- [ ] 일반 프로젝트 목록은 명시적 참여자만 노출한다. 미참여 OWNER도 일반 회계 조회에 접근할 수 없다.
- [ ] 타 팀 멤버, 타 프로젝트 카테고리/파일의 참조를 DB 제약과 서비스 양쪽에서 차단한다.

완료 기준: AC-01/02/08/19의 권한·관계·예산 초기 상태를 확인한다. 공개 장부 발견/참여(P03/P04), 일반 멤버 편집(P08)은 P1로 남긴다.

## 5. 예산과 수동 거래 — 핵심 저장 로직

대상: **B01/B02, H01/H04/H05**. B03 이력 ‘조회’는 P1이지만 이력 ‘저장’은 여기서 구현한다.

- [ ] 예산 UNSET / SET(0) / SET(양수), 설정·해제·재설정·이력·80/100% 도달 상태를 구현한다.
- [ ] 지출/수입·품목·작성자·version·소프트 삭제를 구현한다. 수입 변경은 현재 PROJECT_ADMIN만 허용한다.
- [ ] 명세 §4 및 ERD §7.3의 공통 저장 순서를 사용한다. 수동/OCR/수정/삭제/예산 변경이 같은 프로젝트 잠금 규칙을 공유해야 한다.
- [ ] WARN 확인 토큰은 최신 예산/원장과 재검증하고, BLOCK에서 정확한 한도와 증감 규칙을 적용한다.
- [ ] 명세상 필수 쓰기의 멱등 키, 감사, 예산 이력, 사건/알림 저장을 업무와 함께 커밋한다.
- [ ] 실제 시각·정밀도 기반 중복을 검사한다. 시각 없는 DATE를 임의 00:00으로 바꾸지 않는다.
- [ ] LOCKED 상태 검증을 공통 저장 경로에 둔다. 마감 API는 P1이어도 차단 규칙은 준비한다.

완료 기준: 동시 지출로 BLOCK 한도를 넘지 않음, 동일 키 재전송 저장 1건, 수정된 payload 충돌, 예산 해제/변경 동시 요청, 중복 확정 경쟁, 실패 시 감사/원장 롤백을 실제 MySQL에서 시험한다. 미설정·0원·정확히 100%·감액/삭제 경계값을 포함한다.

## 6. 조회·집계와 프런트 첫 통합

대상: **H02/H03/H06, P12/P13**.

- [ ] 거래 상세·필터·커서 페이징·달력·대시보드·전체 결산을 구현한다.
- [ ] 목록 items와 summary는 같은 읽기 스냅샷을 사용하고, 소계는 전체 필터 결과를 기준으로 한다.
- [ ] 다품목 검색의 JOIN 때문에 거래 금액이 중복 집계되지 않도록 한다.
- [ ] 수입/지출 필터 규칙, 순지출=지출-수입, 잔액=수입-지출, 큰 합계 문자열을 검증한다.
- [ ] 프런트와 가입 → 팀 → 프로젝트 → 수입/지출 → 잔액/결산까지 연결한다.

완료 기준: 빈 목록, 경계 날짜, 복합 필터, 커서 권한, 참여 해제 후 접근 차단을 확인한다. 파일 기능 전에는 마스킹 증빙이 없는 수동 거래 시나리오부터 검증한다.

## 7. 파일·마스킹·OCR

대상: **F01~F07, O01~O04**. 선행: 저장소/OCR 제공자·암호키·마스킹·작업 재시도 정책 확정.

- [ ] 파일 메타데이터/프로젝트 바인딩/거래 증빙과 비동기 작업 상태를 구현한다.
- [ ] 업로드 크기·실제 형식·픽셀 제한·원본 SHA-256을 서버에서 검증한다.
- [ ] 암호화·마스킹 처리 후 표시 파생본만 반환하고, 원본/마스킹 실패 파일은 열람·내보내기·거래 확정에서 차단한다.
- [ ] 파일 스트리밍마다 현재 권한을 확인한다. 미확정 파일은 업로더만 접근한다.
- [ ] OCR 요청 → 처리 → 보정 → 1회 확정을 구현한다. 확정은 5단계의 거래 저장 서비스를 재사용한다.
- [ ] 임시/실패 파일 정리, 작업 재시도, 취소 이후 늦은 콜백을 처리한다. OCR 미확정 값은 원장 합계에 넣지 않는다.

완료 기준: 교차 프로젝트 파일 연결, 원본 노출, 마스킹 실패, OCR 확정 재시도/동시 요청, 파일 삭제 실패와 늦은 완료를 검증한다.

## 8. 앱 내 알림·SSE와 P0 완료

대상: **N01~N04, N11**. 앞 단계에서 저장한 업무 사건/알림 기반을 사용한다.

- [ ] 본인 알림 목록·미확인 수·읽음 처리와 현재 접근권한 재확인을 구현한다.
- [ ] Bearer 기반 fetch streaming SSE, Last-Event-ID, 재생/유실 시 재동기화를 구현한다. 토큰을 query에 넣지 않는다.
- [ ] sid 회수 시 연결을 끊고, 권한 변경·예산 해제 이후 전송 조건을 다시 확인한다.
- [ ] P0 계약 누락을 API 색인으로 대조하고 관련 AC/API 인수 시험을 통합 실행한다.

완료 기준: 이벤트 중복/유실/서버 재시작/세션 회수에서도 알림 목록과 뱃지가 회복된다. P0 대상 작업 모두에 구현·시험 결과가 남아 있다. 문서 구조 검증 보고서를 런타임 시험으로 대신하지 않는다.

## 9. 인증 확장과 재인증 — P1 선행 작업

대상: **A05, A08~A16, S02~S04, S06~S09, S11~S14**. S04 자동 잠금 설정 부분은 P2.

소셜·이메일 보완·비밀번호 재설정·TOTP·복구 코드·기기 세션 관리를 구현한다. 2FA 통과 전 업무 JWT를 발급하지 않고 복구 코드는 성공 시 삭제한다. 소셜 동일 이메일 자동 연동을 금지한다.

재인증 grant는 사용자·sid·action·target·요청 해시에 결합하고 5분/1회용으로 처리한다. 민감 작업 커밋과 원자 소모한다.

완료 기준: 만료/재사용/reset·challenge 목적 혼용이 거절되고 재설정 후 전체 세션이 회수된다. 다음 단계의 출력·삭제에서 재인증을 재사용할 수 있다.

## 11. 확장 기능 — P2

설정 복제(P10), PDF 출력(E 계열), 회원 탈퇴(S15/S16), 자동 잠금 설정/해제(S05/S10)를 구현한다. 복제는 예산 NULL/0/양수 상태를 보존하고 거래·과거 이력을 복사하지 않는다. 탈퇴는 원장·감사를 보존하면서 표시 개인정보와 기존 출력물을 처리한다. 네이티브 생체 인증은 웹 API를 새로 만드는 대상이 아니다.

완료 기준: 전체 기능 50개 추적과 AC-01~28 및 API-01~12를 적용 범위에 맞게 완료한다. 비동기 실패, 권한, 동시성, 보존/삭제 기준을 포함한다.

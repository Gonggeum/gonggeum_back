# 공금이 웹앱 기능 명세서

> 문서 버전: v3.3  
> 최초 작성일: 2026-09-14  
> 개정일: 2026-09-16  
> 시스템: 공금이 공금·정산 관리 플랫폼

> 개정 기준: 기능명세 v3.2의 수정 내용을 기반으로, 목표 예산을 미설정하는 기능을 추가했다. 신규 프로젝트는 예산 미설정을 기본값으로 사용하며, 미설정·0원 설정·양수 설정을 구분한다. 예산 설정/해제, 대시보드, 거래 검증, 알림, 복제, 결산·내보내기, 변경 이력과 인수 기준에 같은 규칙을 적용한다. 팀 직급과 프로젝트 역할은 계속 별도로 관리한다. 본 문서는 기능 기준의 개정본이며 ERD·화면설계 파일이나 실제 앱을 수정·시험 완료했다는 뜻이 아니다. 이전 검토 반영 이력은 부록 A, 이번 변경 이력은 부록 E를 따른다.

## 0. 권한 및 데이터 설계 원칙

### 0.1 팀 레벨 직급

#### 팀 최고 관리자 (`OWNER`)

- 팀 삭제
- 최고 관리자 위임
- 팀원 직급 변경
- 모든 멤버 추방
- 팀 설정 수정

#### 팀 관리자 (`ADMIN`)

- 신규 프로젝트(장부) 개설
- 팀원 초대
- 일반 멤버 추방
- 일반 멤버를 팀 `ADMIN`으로 승격 (다른 `ADMIN` 강등 및 `OWNER` 지정 불가)
- 팀 정보 수정

#### 팀 일반 멤버 (`MEMBER`)

- 팀 정보와 멤버 조회
- 공개 프로젝트 참여
- 팀 자진 탈퇴

> 열람 전용(`VIEWER`) 역할은 사용하지 않는다.

### 0.2 프로젝트 레벨 역할

#### 프로젝트 관리자 (`PROJECT_ADMIN`, 총무)

- 프로젝트의 모든 내역 조회
- 지출 및 수입 등록
- 본인 및 다른 참여자의 거래내역 수정·삭제
- 예산·카테고리 관리
- 프로젝트 마감·잠금
- 결산 자료 내보내기

#### 프로젝트 멤버 (`PROJECT_MEMBER`)

- 프로젝트의 모든 내역 조회
- 본인의 지출 영수증 등록
- 본인이 등록한 지출 내역 수정·삭제
- 수입 등록, 다른 참여자의 거래 수정, 예산·결산 설정은 불가

#### 프로젝트 미참여 팀원

- 비공개 프로젝트 접근 불가
- 비공개 프로젝트 목록 미노출

### 0.3 권한 적용 규칙

- 팀 직급과 프로젝트 역할은 분리하여 관리한다.
- 팀의 `OWNER` 또는 `ADMIN`이라는 이유만으로 모든 프로젝트의 참여 권한을 자동 부여하지 않는다.
- 프로젝트 생성자는 해당 프로젝트의 `PROJECT_ADMIN`으로 자동 등록한다.
- 다른 팀원은 프로젝트 멤버 매핑에 명시적으로 등록되어야 프로젝트에 참여할 수 있다.
- 이 문서에서 **총무**는 해당 프로젝트의 `PROJECT_ADMIN`을 의미한다.
- 팀 `OWNER`의 프로젝트 삭제 등 거버넌스 권한은 프로젝트 참여 권한과 별도로 검증한다.

### 0.4 데이터 처리 규칙

#### 탈퇴·추방 및 거래 보존

- 팀 탈퇴·추방 시 팀원 레코드를 물리 삭제하지 않는다.
- 팀원 상태는 `ACTIVE`, `LEFT`, `KICKED`로 관리하고 종료 일시를 기록한다.
- 기존 거래에는 작성자 식별자와 작성자명 스냅샷을 보존한다.
- 회원 탈퇴로 개인정보가 비식별화된 경우 작성자는 `(탈퇴한 사용자)`로 표시한다.

#### 잔액 계산

- 프로젝트 잔액의 원본 데이터는 거래내역이다.
- 잔액은 `유효한 수입 합계 - 유효한 지출 합계`로 계산한다.
- 성능을 위해 잔액 캐시를 사용할 수 있지만 독립적인 회계 원장으로 취급하지 않는다.
- 잔액 캐시는 거래 저장 트랜잭션 안에서 갱신하고 거래 합계와의 정합성을 검증한다.

#### 감사 로그 보존

- 감사 로그는 프로젝트 하위 데이터와 생명주기를 분리한다.
- 감사 로그는 팀 또는 시스템 범위에 보존한다.
- 프로젝트 삭제 시 감사 로그의 `project_id`는 `NULL`로 처리할 수 있다.
- 모든 관련 감사 로그에 팀·프로젝트 식별자/이름의 **소속 스냅샷**과 행위 대상 유형/식별자/이름의 **대상 스냅샷**을 별도로 기록한다. 삭제 이벤트 한 건만이 아니라 이전 거래·예산·권한 변경 로그에서도 삭제 후 원래 소속과 대상을 식별할 수 있어야 한다. 상세 필수 계약은 §0.10을 따른다.

### 0.5 권한 판정과 마지막 총무 보호

- `팀 관리자 이상`은 해당 팀의 활성 `OWNER/ADMIN`, `프로젝트 참여자`는 활성 팀 멤버십과 해당 프로젝트의 활성 멤버십을 **모두** 가진 사용자를 뜻한다. 총무는 그중 `PROJECT_ADMIN`이다. 본인 거래도 현재 참여·역할·잠금 검증을 생략하지 않는다.
- API가 매 요청 시 권한을 판정한다. 버튼 숨김, JWT의 오래된 역할 값, 과거 작성자라는 사실은 접근 권한의 근거가 되지 않는다. 탈퇴·추방·역할 변경은 다음 요청부터 적용한다.
- 미참여 `OWNER`의 프로젝트 삭제는 팀 설정의 **프로젝트 삭제 관리** 경로에서 수행한다. 이 경로에는 삭제 대상 식별에 필요한 프로젝트 ID·이름·상태만 제공하고 잔액·거래·영수증·결산·참여자 상세를 제공하지 않는다. 일반 프로젝트 목록과 읽기 API는 계속 참여자 전용이다.

| 사용자 상태 | 팀 관리 | 장부 조회·결산 열람 | 지출 수정·삭제 | 수입·예산·내보내기 | 프로젝트 영구삭제 |
| --- | --- | --- | --- | --- | --- |
| 팀 ADMIN + 프로젝트 MEMBER | 팀 ADMIN 범위 | 허용 | 본인 지출만 | 불가 | 불가 |
| 팀 MEMBER + 프로젝트 ADMIN | 팀 조회·본인 탈퇴 | 허용 | 모든 지출 | 허용 | 불가 |
| 팀 OWNER + 프로젝트 미참여 | OWNER 범위 | 불가 | 불가 | 불가 | 별도 삭제 관리에서 허용 |
| 팀 MEMBER + 프로젝트 미참여 | 팀 조회·본인 탈퇴 | 비공개 목록·내용 모두 불가 | 불가 | 불가 | 불가 |
| 프로젝트 LOCKED의 활성 참여자 | 팀 직급에 따름 | 허용 | 본인·총무 모두 불가 | 수입·예산 변경 불가, 총무 내보내기는 허용 | 팀 OWNER만 가능 |

**마지막 총무 처리 — 이번 개정에서 구체화한 정책:** 삭제 중이 아닌 모든 프로젝트는 활성 총무를 최소 1명 유지한다. 마지막 총무의 프로젝트 제외·강등, 팀 탈퇴·추방, 회원 탈퇴를 실행하려면 먼저 현재 총무가 활성 프로젝트 참여자 중 후임을 지정해야 한다(F-PROJ-04). 팀 OWNER에게 총무 권한을 자동 부여하지 않는다. 후임을 둘 수 없으면 OWNER가 기존 삭제 권한으로 해당 프로젝트를 영구삭제한 후 이탈을 진행한다. 잠긴 장부에서도 후임 지정은 허용하되 회계 데이터 변경은 금지한다.

여러 프로젝트에 영향을 주는 이탈은 전체 대상을 사전 검증하고 동일 작업에서 원자적으로 처리한다. 하나라도 마지막 총무 조건에 걸리면 부분 탈퇴·부분 추방 없이 `409 LAST_PROJECT_ADMIN`을 반환한다. 권한이 없는 요청자에게 차단 사유와 해결 안내만 제공하고 비공개 장부 상세는 노출하지 않는다. 팀 전체 영구삭제 시 함께 삭제되는 프로젝트에는 후임을 요구하지 않는다. 동시 후임 변경·이탈도 §0.7의 잠금 순서에 포함한다.

### 0.6 예산 계산·알림·초과 정책

목표 예산은 선택 기능이다. 프로젝트와 예산의 관리 단위는 프로젝트이며, 팀의 예산 설정으로 다른 프로젝트에 자동 적용하지 않는다. 프로젝트 생성·거래 등록·결산·내보내기는 목표 예산 설정 완료를 사전 조건으로 요구하지 않는다.

| 항목 | 확정 계약 |
| --- | --- |
| 금액·집계 | KRW 정수. 목표 예산 T는 미설정이면 NULL, 설정하면 0~1,000,000,000원이다. 유효 지출 합계 E는 소프트 삭제되지 않은 확정 지출만 합산한다. 미확정 OCR은 제외한다. 수입은 잔액에만 반영하며 예산 소진율의 분모·분자를 바꾸지 않는다. |
| 저장값·상태 | 프로젝트별 `target_budget`은 NULL을 허용한다. NULL은 `UNSET`(미설정), 0을 포함한 정수는 `SET`(설정)이며 상태는 금액에서 도출한다. API 응답의 `budget_configured`는 T가 NULL이 아닌지로 판정한다. 별도 상태 컬럼을 사용하더라도 상태·금액의 일치 제약을 보장해야 한다. 빈 문자열이나 0으로 미설정을 대신하지 않는다. |
| 신규 프로젝트 기본값 | `target_budget=NULL`, `over_budget_policy=WARN`, `warning_enabled=true`, `critical_enabled=true`로 생성한다. 기준값은 고정 80/100이다. 정책과 두 알림 설정값은 보존하되 미설정에서는 적용하지 않는다. 개인의 `budget_alert_enabled`와 대체 관계가 아니다. |
| UNSET: T IS NULL | 잔액·총수입·총지출·거래·카테고리 통계는 정상 제공한다. 예산 소진율·초과액·예산 잔여액은 계산하지 않고 API에 NULL로 반환한다. 화면에는 `목표 예산 미설정`을 표시하고 게이지·초과 경고·예산에 따른 지출 차단·80/100% 임계 알림을 적용하지 않는다. 거래 금액 상한·권한·잠금·중복·날짜 검증은 그대로 유지한다. |
| SET: T > 0 | 소진율 = E/T×100. 계산·판정에는 반올림 전 값을 사용한다. 80% 이상 100% 미만은 주황, 100% 이상은 빨강이며, 100% 초과 수치도 그대로 표시한다. |
| SET: T = 0 | **0원은 실제 목표 예산 0원이며 미설정이 아니다.** 소진율은 NULL로 반환하고 화면은 `— (목표 예산 0원)`으로 표시한다. 80/100% 임계 알림은 만들지 않는다. 지출이 있으면 금액과 `예산 초과`를 표시한다. 두 알림 설정값은 보존하고 양수 예산으로 바뀌면 다시 적용한다. |
| WARN | 예산 SET인 경우에만 적용한다. 요청 적용 후 지출 E′가 T를 초과하고 지출이 증가하면 현재 지출·예상 지출·목표 예산·초과액을 보여 주고 확인받는다. 확인은 해당 저장 내용과 예산 상태에 결합한다. 재검증 결과가 바뀌면 최신 값으로 다시 확인한다. UNSET에서는 WARN 확인을 요구하지 않는다. |
| BLOCK | 예산 SET인 경우에만 적용한다. 지출 증가 요청에서 E′ > T이면 저장을 거절한다. 정확히 T인 경우는 허용한다. T=0이면 양수 지출 신규 등록·증액은 차단한다. 기존 초과 지출의 감액·삭제 또는 총액이 늘지 않는 정정은 허용한다. UNSET에서는 보존된 정책이 BLOCK이어도 예산에 따른 차단을 하지 않는다. |
| 예산 설정·변경 | 미설정 프로젝트에 예산을 설정하거나 예산 감액/BLOCK 전환을 하면 기존 지출이 새 예산보다 클 수 있다. 사유와 초과 안내를 확인한 후 설정은 저장하되 기존 거래를 삭제·취소하지 않는다. 이후 지출 증가에는 새 정책을 적용한다. 처음부터 과거 거래를 새로 등록하거나 거래 잔액을 변경하지 않는다. |
| 예산 해제 | SET→UNSET 시 기존 예산액과 영향 안내를 확인하고 변경 사유를 입력한다. `target_budget=NULL`로 저장하며, 소진율·초과 표시·임계 이벤트 상태를 비활성화한다. 기존 거래·잔액·변경 이력·이미 생성된 알림은 삭제하지 않는다. 초과 정책·80/100 알림 ON/OFF는 다음 설정을 위한 값으로 보존하며 예산 해제 중에는 적용하지 않는다. |
| 임계 이벤트 | T>0에서 활성 기준의 미도달→도달 전환에만 1회 생성한다. UNSET/0원에서 양수 예산을 설정하거나 기준을 활성화한 결과 이미 임계치에 도달했다면, 현재 전체 유효 지출로 1회 생성한다. 계속 도달 중이면 반복하지 않고, 내려갔다 재도달하면 새 이벤트다. 해제는 도달 상태를 비활성으로 바꾸고, 이후 재설정은 새 전환으로 판정한다. 두 기준을 동시에 넘으면 1건에 두 도달 정보를 담는다. 재시도는 동일 이벤트 ID로 중복 제거한다. |
| 수신자·발송 | 저장 시점의 활성 프로젝트 참여자에게 앱 내 알림을 생성한다. 개인 푸시 토글은 외부 푸시 발송만 제어한다. UNSET·T=0·프로젝트 기준 OFF이면 그 임계 이벤트 자체가 없다. 해제 후 아직 전송되지 않은 예산 푸시와 다이제스트 대상은 발송 직전 현재 예산 상태를 확인하여 제외한다. 일반 거래 알림은 계속 생성한다. 본인 행위 푸시 억제·방해금지 정책은 §0.12를 따른다. |
| 카테고리 배분 예산 | 카테고리의 선택 배분 예산은 총 목표 예산과 별개다. 총 목표 예산 미설정이어도 카테고리·배분 금액을 관리할 수 있지만, 이를 합산해 총 목표 예산을 자동 설정하거나 지출 차단·임계 알림 근거로 사용하지 않는다. 목표 예산 해제 시 카테고리와 배분 금액은 보존한다. |

#### 0.6.1 예산 상태 전환·입력·이력

| 전환/요청 | 입력·검증 | 저장·표시 결과 |
| --- | --- | --- |
| 생성 기본값/나중에 설정 | 목표 예산 입력을 건너뛸 수 있다. 빈 입력을 실제 0원으로 바꾸지 않는다. | UNSET, T=NULL. 즉시 프로젝트 사용 가능. 생성 기본 상태는 변경 이력의 기준값이며 별도 수동 변경 사유를 요구하지 않는다. |
| UNSET→SET | `[목표 예산 설정]`을 선택하면 금액은 필수이며 0~10억 정수만 허용한다. 최초 설정의 사유는 `최초 목표 예산 설정`을 기본 제공한다. 해제 후 재설정은 변경 사유를 필수 입력한다. | T와 정책·알림 설정 저장, 기존 전체 유효 지출로 재계산. 기존 초과액은 안내하되 설정 자체를 거절하지 않는다. |
| SET→SET | 금액 증감은 변경 사유 필수. 정책·알림 설정도 저장하며 해당 필드의 전후 값을 감사에 기록한다. | 새 예산에 따라 재계산·검증. 거래는 유지한다. |
| SET→UNSET | `[목표 예산 미설정으로 전환]` 확인과 공백이 아닌 변경 사유 필수. | T=NULL, 예산 기능 비활성. 정책·알림 선택값과 회계 데이터는 보존한다. |
| UNSET→UNSET | 동일 설정 저장/재시도는 멱등 처리한다. | 금액이나 예산 변경 사건을 새로 만들지 않는다. |

설정 API는 `budget_mode=SET/UNSET`을 명시적으로 받는다. SET이면 `target_budget`은 필수 정수이며 누락·NULL·빈 문자열을 400으로 거절한다. UNSET이면 `target_budget`은 NULL 또는 생략만 허용하고 숫자를 함께 보낸 모순 요청은 400으로 거절한다. 수정 요청에서 예산 필드 자체가 생략되면 기존 예산 상태를 유지하며 이를 해제로 해석하지 않는다. 해제 후 재설정 폼은 마지막 금액을 자동 적용하지 않고 사용자가 새 금액을 확인·입력하게 한다.

최초 설정·금액 변경·해제·재설정은 F-PROJ-02의 P0 범위다. F-PROJ-08의 통합 수정 화면이 후속 제공되더라도 예산 상태 전환 기능과 필수 저장·이력은 P0부터 제공한다. 잠금 LOCKED/삭제 진행 DELETING에서는 설정·변경·해제를 모두 차단한다. 팀 직급과 무관하게 해당 프로젝트의 PROJECT_ADMIN만 실행할 수 있다.

예산 변경 이력은 `INITIAL_SET / AMOUNT_CHANGED / UNSET / RESET / SETTINGS_CHANGED` 유형, 변경 전·후 설정 여부·금액(NULL 허용), 정책·알림 설정 전후 값, 행위자, 시각, 사유를 보존한다. 금액·설정 여부가 그대로이고 정책/알림 선택만 바뀌면 SETTINGS_CHANGED를 사용하며 사유는 선택이다. 동일 값 저장은 새 이력을 만들지 않는다. NULL을 0원으로 치환하지 않으며, 화면에서는 `미설정→100,000원`, `100,000원→미설정`, `미설정→0원`을 서로 구분한다. 감사 로그와 이력 저장은 예산 저장과 같은 트랜잭션에서 확정한다. 설정 화면 저장과 외부 알림 발송 성공은 별개이며, 알림 실패로 확정된 거래·설정을 취소하지 않는다. 동시 변경·거래 저장은 §0.7을 따른다.

### 0.7 작성자 무결성과 동시 저장

1. 서버가 인증 사용자에서 작성자 사용자 ID와 해당 프로젝트의 활성 프로젝트 멤버십 ID를 도출한다. 클라이언트가 다른 등록자 ID를 지정할 수 없다. 거래의 프로젝트 = 등록자 멤버십의 프로젝트, 등록자 사용자 = 해당 멤버십의 팀원 사용자, 팀원 소속 팀 = 프로젝트 소속 팀을 보장한다.
2. 카테고리·OCR 작업·증빙 파일·수정/삭제 대상은 모두 요청 프로젝트와 일치하고 요청자가 사용 가능한 대상이어야 한다. 예산 변경자·삭제자 등 행위자도 인증 문맥에서 결정한다. 기존 작성자는 수정자가 바꾸지 않는다. 탈퇴 후 비활성 멤버십과 작성자 스냅샷은 과거 거래 참조로 유효하다.
3. 같은 프로젝트의 거래 등록(OCR/수동)·수정·삭제, 예산 설정 변경, 마감·해제, 멤버 변경, 삭제 전환은 공통 프로젝트 행 잠금 또는 동등한 직렬화 수단을 사용한다. 팀 단위 이탈·삭제는 먼저 팀을 잠그고 프로젝트 ID 순서로 잠근다. 모든 관련 쓰기에서 동일 순서를 사용해 경쟁을 조정한다.
4. 잠금 획득 후 최신 팀/프로젝트 상태와 권한을 재검증하고, 유효 거래 합계와 중복 여부를 조회한 뒤 예산 정책을 판정한다. **검증→거래/설정 저장→합계/캐시 갱신→필수 감사·알림 발송 대기 기록**을 하나의 DB 트랜잭션으로 확정한다. 외부 OCR·파일 처리와 네트워크 알림 전송은 이 트랜잭션 안에서 기다리지 않는다.
5. 개별 거래의 `version`은 동일 거래 수정 충돌 검출에 사용하며 공통 잠금을 대신하지 않는다. 수정 충돌은 `409 VERSION_CONFLICT`와 재조회 안내로 처리한다. 저장 재시도는 사용자·프로젝트·요청 내용에 결합된 요청 키로 기존 결과를 반환하여 중복 거래/알림을 만들지 않는다. 다른 내용으로 같은 키를 재사용하면 거절한다.
6. 프런트의 3초 연타 방지는 보조 수단이다. 잠금 전 검증을 통과했어도 저장 시 `LOCKED`, `DELETING`, 권한 상실, 예산 초과, 중복이면 저장하지 않고 해당 사유를 안내한다.

### 0.8 OCR 중복 판정과 회계 기준일

- **판정식:** 같은 프로젝트의 유효 지출에 대해 `동일 원본 파일 SHA-256` **또는** `정규화 가맹점 + 실제 거래 일시 + 총결제금액`이 모두 일치하면 확정 중복이다. `409 DUPLICATE_RECEIPT`로 차단하며 사용자 확인 버튼으로 강제 등록할 수 없다. OCR 확정·수동 증빙 등록·거래 수정에 같은 검증을 적용하고 수정 중인 자기 거래는 비교에서 제외한다.
- 파일 해시는 업로드 원본 바이트를 기준으로 서버가 검증한다. 크롭·압축된 파생 이미지 해시와 구분한다. 가맹점은 사업자번호가 있으면 이를 우선하고, 없으면 상호의 앞뒤 공백·연속 공백·영문 대소문자를 정규화한다. 금액은 KRW 정수다. 실제 일시는 시간대와 원문의 정밀도를 보존하며, 분 단위 자료의 초를 임의로 보충하지 않는다. 서로 다른 정밀도는 확정 일치로 간주하지 않고 확인 대상으로 처리한다.
- **같은 날짜·같은 금액만으로는 중복이 아니다.** 시각이 없는 영수증에 00:00을 만들어 넣지 않는다. 시각이 없으면 파일 해시로 확정 중복을 판정하고, 날짜·상호·금액만 같은 경우 보정 안내를 제공한다. 미확정 유사 후보는 확정 중복 차단과 구분한다. 같은 날 서로 다른 실제 시각의 정상 결제는 허용한다.
- 저장 직전 §0.7의 공통 잠금 안에서 재검사한다. 삭제된 지출은 유효 중복 집합에서 제외하되 같은 저장 요청의 재시도는 새 거래를 생성하지 않는다. OCR 작업은 한 번만 거래로 확정한다.
- 회계 집계는 `business_date` 기준이며 기본 업무 시간대는 `Asia/Seoul`이다. 서버 생성 시각은 UTC로 저장할 수 있지만 이를 임의 변환해 회계일자를 바꾸지 않는다. 수동 입력은 날짜 필수·실제 시각 선택이다. 미래 회계일자는 차단한다. 프로젝트 기간 밖의 과거 거래는 확인 안내 후 저장할 수 있으며 달력에서 조회 가능해야 한다.
- 원문의 ‘텍스트 추출률 30%’는 분모가 정의되지 않아 그대로 구현 기준으로 사용하지 않는다. 엔진이 표준화된 0~1 신뢰도를 제공하면 `<0.30`을 저품질 안내 기준으로 사용한다. 해당 지표가 없으면 엔진 실패·필수 항목 추출 실패를 기준으로 수동전환을 제안한다. 낮은 신뢰도 필드는 강조하고 사용자가 보정·필수값 검증을 완료해야 확정한다.

### 0.9 인증 단계·토큰 무효화

- 비밀번호 또는 기존 소셜 인증 성공은 1차 인증이다. 2FA 미활성 계정만 즉시 정상 JWT를 발급한다. 활성 계정은 유효기간 5분의 2FA 전용 challenge로 OTP 또는 1회용 복구 코드를 검증한 후 정상 Access Token(2시간)·Refresh Token(14일)을 발급한다. challenge는 일반 업무 API에 사용할 수 없고 계정·인증 목적·로그인 시도에 결합한다. OTP 5회 연속 실패 시 5분 잠금 후 새 challenge를 요구한다.
- 로그인 성공은 전체 필수 인증이 완료된 시점이다. 1차 실패·2FA 실패·잠금은 각각 이력에 남긴다. 비밀번호 5회 연속 실패 시 5분 잠금이 끝나고 CAPTCHA를 통과해야 재시도할 수 있다. CAPTCHA는 잠금 시간·비밀번호·OTP를 대체하지 않는다.
- 비밀번호 재설정은 `RESET_CODE`(6자리, 5분)와 `RESET_GRANT`(충분한 난수, 10분)로 구분한다. 코드/토큰을 평문 저장하지 않고 계정·목적·challenge ID에 결합해 키 기반 해시로 검증한다. 재발급은 이전 코드를 무효화하고 60초 간격, 5회 오입력 한도를 적용한다. 코드 검증 성공 시 코드를 원자적으로 소모하며 연결된 grant 하나를 발급한다. 비밀번호 갱신과 grant 소모·전체 세션 무효화도 원자적으로 처리한다. 재설정만으로 자동 로그인하지 않는다.
- JWT는 서버의 세션 식별자 `sid`에 결합한다. 보호 API는 토큰 서명/만료뿐 아니라 활성 세션 상태도 확인한다. 로그아웃·원격 종료·비밀번호 재설정·회원 탈퇴는 refresh와 기존 access 모두 즉시 사용 불가하게 한다. 개별 access 블랙리스트는 만료까지 유지한다. 로그아웃 API 요청은 인증 정보를 제거하기 전에 전송하고, 네트워크 실패 시 서버 종료 미확정을 안내한다.
- 재인증은 해당 작업 권한 검증을 대체하지 않는다. 비밀번호 또는 소셜 재인증 + **2FA 활성 계정에만** OTP를 요구한다. 재인증 결과는 사용자·대상·행위에 결합한 5분 유효 1회용 권한으로 실행 직전 확인한다.
- 복구 코드는 해시로 저장하고 사용 성공 트랜잭션에서 해당 해시 레코드를 삭제한다. 코드 없는 사용 사건 로그는 남길 수 있다. `used_at`만 기록한 채 사용된 코드 해시를 유지하는 구현은 허용하지 않는다.

### 0.10 감사·영구삭제 생명주기

감사 로그의 최소 필수값은 시각, 행위자, 행위 유형, 결과, 대상 스냅샷, `team_id_snapshot/team_name_snapshot`, 프로젝트 관련 행위의 `project_id_snapshot/project_name_snapshot`, 필요한 변경 전·후 값이다. 팀 자체 사건의 프로젝트 스냅샷은 비워 둔다. 사용자 비밀번호·토큰·OTP·마스킹 전 개인정보는 로그에 남기지 않는다. 소속 이름은 사건 발생 시점 값이며 기존 로그를 현재 이름으로 덮어쓰지 않는다.

팀 감사 조회는 팀 직급 변경·초대·추방 등 팀 운영 사건을 팀 관리자에게 제공한다. 프로젝트 거래·예산 상세 감사는 해당 프로젝트 총무만 조회한다. 팀 OWNER도 미참여 프로젝트 회계 감사를 조회할 수 없다. 영구삭제 후 로그는 시스템 보존 범위에서 유지하며, 삭제된 프로젝트의 과거 역할을 근거로 사용자 조회 권한을 계속 인정하지 않는다.

팀/프로젝트 삭제는 복구 가능한 휴지통이 없는 **영구삭제**다. 다만 DB와 외부 저장소를 하나의 원자적 트랜잭션으로 삭제했다고 간주하지 않는다.

1. 권한·재인증·대상명 일치를 확인한 후 공통 잠금 안에서 대상(팀 삭제는 하위 프로젝트 포함)을 `DELETING`으로 전환한다. 신규 접근·업로드·OCR 확정·내보내기 생성/다운로드를 차단한다. 기존 작업 ID, 파일 키, 감사 소속 스냅샷, 최소 알림 수신자를 정리 작업에 보관한다. 이 작업 레코드는 삭제 대상 하위 CASCADE에 넣지 않는다.
2. 진행 중 OCR/내보내기를 취소한다. 늦게 도착한 콜백·완료 업로드는 상태를 재검증하여 거래/다운로드를 부활시키지 않고 결과 파일을 정리한다.
3. 아래 순서와 참조 정책으로 DB를 정리한다. 감사 로그는 소속·대상 스냅샷이 있는지 먼저 확인하고 FK만 NULL 처리한다.
4. 참조가 없는 파일의 외부 객체·파생 이미지·캐시·생성 결과를 삭제한다. 다른 활성 업무가 정당하게 참조하는 공유 객체는 남기고 삭제 대상 연결만 제거한다. 단, 삭제 프로젝트 회계 내용이 포함된 **생성 내보내기 파일**은 다른 프로젝트와 공유해 계속 제공하지 않는다.
5. 외부 삭제 실패는 오류·재시도 횟수를 기록하고 재시도한다. UI는 `삭제 처리 중/정리 실패(재시도 중)/삭제 완료`를 구분한다. 삭제 수락(예: 202)은 영구삭제 완료가 아니다. 실패 중에도 접근은 닫혀 있고 복원되지 않는다. 필수 정리가 완료된 뒤 대상 DB 식별 레코드와 작업의 임시 개인정보를 정리한다.

| 순서·대상 | 삭제/참조 계약 |
| --- | --- |
| OCR 작업 | 먼저 취소·확정 차단. OCR의 거래 참조 등 순환 참조는 해제한 뒤 작업·임시 파싱 데이터·미확정 업로드를 삭제한다. |
| 내보내기 작업 | 상태/다운로드 권한 무효화 → 결과 파일 키 확보 → 작업·대상 연결 정리. `project_id SET NULL`만 하고 파일을 계속 제공하지 않는다. |
| 거래 하위 | 품목·지출/수입 상세·첨부 연결 등을 거래보다 먼저 삭제하거나 검증된 CASCADE 적용. 거래 수정·삭제 이력 중 보존 대상은 별도 감사 저장소로 보존한다. |
| 카테고리·예산 | 참조 거래 정리 후 카테고리·예산 설정·운영상 변경 이력 정리. 감사 사본은 보존한다. |
| 프로젝트 멤버십 | OCR/거래 참조 정리 후 삭제. 프로젝트를 먼저 지워 작성자 FK 위반을 만들지 않는다. |
| 팀 하위 | 팀 초대·팀 정보·팀원은 관련 프로젝트 정리 후 삭제. 사용자 계정은 팀 삭제로 삭제하지 않는다. |
| 알림 | 프로젝트/거래 FK는 NULL 또는 비활성 대상으로 처리하고 본문 회계 내용을 제거한다. 삭제 알림은 사전에 확보한 수신자와 최소 이름 스냅샷으로 생성한다. |
| 감사 로그 | 팀/프로젝트 FK는 SET NULL 가능, 필수 소속·대상 스냅샷 유지. 프로젝트/팀 CASCADE에 포함 금지. |
| 파일 저장소 | 연결 해제 후 유효 참조 수 확인. 비공유 객체 삭제와 `stored_files` 정리, 공유 객체의 타 업무 참조 보존. 삭제 작업 키는 완료까지 유지한다. |

영수증·내보내기 링크는 인증과 현재 프로젝트 접근권한을 확인하는 다운로드 경로를 사용한다. 삭제·권한 회수 후 기존 링크로 재접근할 수 없어야 하며 공개 영구 URL을 만들지 않는다. 이미 사용자 기기에 다운로드된 사본은 서버에서 회수할 수 없다.

### 0.11 회원 탈퇴 정리 계약

회원 탈퇴는 팀 OWNER 승계와 마지막 총무 보호를 **모두** 검증한 후 실행한다. 프로젝트·팀 자체 삭제와 달리 회계 자료는 보존한다.

| 대상 | 처리 |
| --- | --- |
| 사용자 기준 레코드 | 비식별 tombstone으로 유지해 회계 작성자 FK를 보존한다. ID·이메일·이름 등 로그인/프로필 식별값은 삭제·비식별화하고 계정을 사용 불가 처리한다. |
| 프로필 이미지·개인 설정 | 개인 연결 삭제 및 비공유 파일 정리. 회계 증빙으로 정당하게 공유된 파일은 회계 자료 정책을 적용한다. |
| 비밀번호·소셜 연결·보안키 | 비밀번호 해시, 소셜 연결, 저장된 provider 토큰, 2FA 시크릿, 미사용 복구 코드, 재설정·재인증 challenge 삭제/무효화. |
| 약관 동의·개인 알림 | 사용자 연결 약관 동의 정보·알림 설정·개인 알림·푸시 구독 삭제. 탈퇴 사건 기록에는 약관 전문이나 동의 개인정보를 복제하지 않는다. |
| 세션·로그인 이력 | 전체 세션 즉시 폐기 및 access 차단. 개인 로그인 이력의 IP/기기 등 식별정보 삭제·비식별화. 회계 감사와 동일한 무기한 보존 대상으로 취급하지 않는다. |
| 팀·프로젝트 멤버십 | 활성 팀원은 LEFT와 종료 시각, 활성 프로젝트 멤버십은 INACTIVE로 전환. 기존 종료 이력은 유지한다. 재가입·재초대는 새로운 멤버십을 만든다. |
| 기존 거래·회계 감사 | 작성자 사용자 식별자와 등록 당시 이름 스냅샷을 보존한다. 화면·API·검색·내보내기에서 이름은 `(탈퇴한 사용자)`로 반환한다. 일반 응답에 원래 이름 스냅샷을 함께 노출하지 않는다. |
| 진행 중 개인 작업 | 미확정 OCR·미완료 내보내기·예약 알림의 실행권한을 회수하고 늦은 완료를 차단한다. 확정 회계 증빙은 보존한다. |

### 0.12 도입 단계·웹앱 공통 동작

| 구분 | P0에 필요한 기반 | 후속 UI/확장 |
| --- | --- | --- |
| 목표 예산 | 미설정 기본값, F-PROJ-02 설정·변경·해제·재설정, 예산 상태별 거래 검증, 변경 이력·감사 저장 | F-PROJ-08 기본 정보와 예산의 통합 수정 화면 P1 |
| 로그인 | `login_histories` 및 성공/실패 기록, 세션 취소 | F-SEC-04 이력 조회·원격 종료 UI P1 |
| 알림 | 가입 시 `notification_settings` 기본 레코드(유형별 true, 방해금지 OFF), 앱 내 알림·읽음·실시간 수신 | F-NOTI-04 개별 설정 UI·웹 푸시 구독·다이제스트 P1 |
| 감사 | `audit_logs` 최소 필드와 P0 기능의 감사 기록 | F-SEC-07 검색·조회 UI P1 |
| 영수증 보호 | F-SEC-05 마스킹, F-SEC-08 암호화 | 모바일 생체 인증 등은 별도 P2 |

P0/P1/P2는 구현 우선순위다. P0에서 요구한 저장 결과를 P1 조회 UI와 함께 뒤로 미룰 수 없다. P1 기능을 제공하는 시점에는 관련 인증·무결성·상태 처리가 모두 작동해야 한다.

- **웹 알림:** 앱 내 알림과 WebSocket/SSE는 P0. 외부 웹 푸시는 P1이며 사용자가 허용한 브라우저의 구독으로 발송한다. 팀 초대·지출 등록·예산·직급 변경 토글은 독립이다. 전체 `push_enabled`와 해당 유형 토글이 모두 ON이고 유효 구독이 있을 때 외부 푸시를 발송한다. 현 범위의 `in_app_enabled`는 true로 유지하며 푸시 토글로 앱 내 사건 기록을 없애지 않는다. 본인 행위는 외부 푸시만 억제하고, 앱 내 이벤트는 유지한다. 알림 전송은 사건 ID+수신자+채널로 중복 제거하고 실패 재시도 상태를 관리한다. 방해금지 종료에는 채널별로 1건의 요약을 생성한다. 네이티브 FCM/APNs와 생체 인증은 해당 앱을 제공할 때만 적용하며 웹 MVP 의존성이 아니다.
- **무소속·목록:** 로그인 후 활성 소속 팀이 없으면 팀 만들기/초대 코드 입력을 제공한다. 팀 선택 목록은 활성 팀 멤버십으로 구성한다. 일반 프로젝트 목록은 참여 프로젝트만 반환한다. `TEAM_ALL` 공개 프로젝트 중 미참여자가 직접 참여 가능한 것은 별도 공개 참여 목록에 최소 이름·설명만 표시하고, 참여 요청 성공으로 명시적 멤버십을 만든 뒤 장부에 진입한다. `SELECTED`는 이 목록에도 노출하지 않는다. 이 목록들은 기존 팀·프로젝트 기능의 진입 상태이며 독립적으로 존재하지 않는 기능 ID를 붙이지 않는다.
- **모달·반응형:** 거래 상세/OCR 모달을 닫으면 호출 화면·필터·스크롤·달력 월/선택일을 복원한다. 넓은 화면 OCR은 원본/입력 폼 좌우 분할, 좁은 화면은 탭/세로 배치와 같은 필드 하이라이트를 제공한다. 스와이프·길게 누르기에 버튼·키보드 대체 조작을 제공한다.
- **민감 이미지:** 사용자에게 제공하는 원본 뷰어·썸네일·내보내기 증빙은 F-SEC-05에 따라 민감정보가 가려진 표시용 이미지다. 마스킹 전 업로드는 접근 제한된 처리용 임시본이며 파생본 확정 후 정리한다. ‘원본 보기’는 영수증 전체 해상도 보기로, 민감정보 노출 허가를 뜻하지 않는다. 마스킹이 실패하면 재처리/재업로드 안내 후 배포·거래 확정을 보류한다.

## 2. 상세 기능 명세서 (대분류별)

### 대분류 1. 회원 가입 및 계정 인증

| F-AUTH-01. \[이메일 회원 가입\] 비회원 전체 P0 (필수) |  |
| ----- | :---- |
| **대상 데이터** | '사용자', '사용자 정보', '기본 정보', '약관 동의 정보', '알림 설정' |
| **사전 조건** | 비로그인 상태에서 회원가입 화면에 진입했을 때 |
| **상세 동작 시나리오** | 사용자가 '기본 정보' 항목('사용자 ID', '이메일', '비밀번호', '비밀번호 확인', '이름', 프로필 사진)을 입력한다. `F-AUTH-02 [중복 확인]`을 통과하고, `F-AUTH-03 [약관 동의]`의 필수 항목을 체크한 후 `[가입하기]`를 클릭한다. **\[서버 최종 무결성 검증\]:** 클라이언트 검증과 별개로 서버에서 아이디/이메일 중복 및 비밀번호 정규식을 재검증한다. (동시 가입 충돌 방지) 검증 통과 시 트랜잭션(Transaction) 단위로 DB에 레코드를 일괄 생성한다: '기본 정보': '사용자 ID', '이메일', 단방향 해시 암호화(bcrypt/Argon2)된 '비밀번호', '이름', '프로필 이미지' '약관 동의 정보': 동의한 각 약관의 식별자, 약관 버전(`v1.0`), '약관 동의 일시' '알림 설정': 기본 알림 수신 설정 (유형별 수신 설정 ON, 앱 내 알림 ON, 외부 푸시는 브라우저 동의/구독 후 발송) **\[회원가입 후 처리 정책\]:** 가입 성공 즉시 정식 인증 토큰(JWT)을 발급하여 **자동 로그인 처리** 후 초대 문맥이 있으면 동일 초대 확인으로, 없으면 온보딩(팀 생성 또는 초대 코드 입력)으로 이동한다. |
| **입력 데이터 (Input)** | '사용자 ID' (필수, 영문 소문자/숫자 조합 4\~20자, 특수문자 불가) '이메일' (필수, RFC 5322 표준 규격) '비밀번호' (필수, 8\~20자 영문 대소문자/숫자/특수문자 중 3종 이상 조합) '비밀번호 확인' (필수, 비밀번호와 100% 일치) '이름' (필수, 한글/영문 2\~20자) '프로필 이미지' (선택, 최대 5MB, JPG/PNG) '약관 동의 정보' (필수 약관 2종 동의 체크) |
| **출력 데이터 (Output)** | DB 내 신규 '사용자', '사용자 정보', '기본 정보', '약관 동의 정보', '알림 설정' 레코드 생성, JWT 발급 |
| **예외 및 엣지 케이스** | **중복 가입 경합(Race Condition):** 중복확인을 통과했으나 제출 시점에 동일 아이디/이메일이 생성된 경우 DB Unique Index 위반 에러를 캐치하여 *"방금 다른 사용자가 등록한 아이디/이메일입니다."* 안내. **공백 입력 방지:** 아이디 및 이메일 앞뒤 공백(Trim) 자동 제거 및 이메일 소문자(lowercase) 자동 정규화. |
| **가입 원자성 및 복귀** | 사용자·기본 정보·필수 약관 동의·기본 알림 설정을 가입 트랜잭션에서 함께 생성한다. 초대 링크/코드로 진입했다면 가입 후 동일 초대 확인 화면으로 돌아가며 자동 수락하지 않는다. 초대 맥락이 없고 소속 팀이 없으면 §0.12의 온보딩으로 이동한다. |

| ----- | :---- |
| **대상 데이터** | '기본 정보' ('사용자 ID', '이메일') |
| **사전 조건** | 회원가입 화면에서 '사용자 ID' 또는 '이메일'을 입력했을 때 |
| **상세 동작 시나리오** | 사용자가 '사용자 ID' 또는 '이메일'을 입력하고 `[중복확인]` 버튼을 클릭한다. 형식 유효성 검사(정규식)를 통과한 경우에 한해 서버에 비동기 중복 검사를 요청한다. (형식 미달 시 요청 차단) 서버 DB 조회 결과 사용 가능(`True`) 시 입력창 테두리를 초록색으로 변경하고 *"사용 가능한 아이디(이메일)입니다."* 표시 및 인증 상태를 완료(`isVerified: True`)로 설정한다. 이미 존재하는 경우(`False`) 붉은색 테두리와 함께 *"이미 사용 중인 아이디(이메일)입니다."* 표시. |
| **입력 데이터 (Input)** | '사용자 ID' 또는 '이메일' 문자열 |
| **출력 데이터 (Output)** | 사용 가능 여부 (`isAvailable: Boolean`), 피드백 메시지 |
| **예외 및 엣지 케이스** | **수정 후 재검증 누락 방지 (Dirty State 관리):** 중복 확인을 완료한 후 사용자가 텍스트를 1글자라도 수정하면 `isVerified` 상태가 즉시 `False`로 변경되어 가입 버튼이 다시 비활성화됨. |

| F-AUTH-04. \[소셜 간편 가입 / 로그인\] 비회원 전체 P1 (주요) |  |
| ----- | :---- |

| ----- | :---- |

| **목표 예산 미설정과 알림** | 개인의 예산 푸시 토글이 ON이어도 미설정/0원 프로젝트에서는 80/100% 임계 이벤트가 생성되지 않는다. 미설정 전환 시 개인 토글은 변경하지 않는다. 이미 생성된 과거 예산 알림은 사건 당시 내용으로 보존하되 딥링크는 현재 대시보드를 보여 준다. 아직 전송되지 않은 예산 푸시·다이제스트는 현재 프로젝트 예산 상태를 확인하여 미설정이면 제외한다. |

## 부록 E. v3.3 변경 이력 — 목표 예산 미설정

개정일: 2026-09-16. 기준 파일: 공금이_웹앱_기능명세서_v3.2.md. 사용자 요청에 따라 목표 예산을 미설정할 수 있는 기능을 추가하고 관련 동작을 일치시켰다.

| 항목 | v3.2 | v3.3 |
| --- | --- | --- |
| 목표 예산 선택 | 0~10억 원 입력, 별도 미설정 없음 | 선택 기능. SET일 때만 금액 필수, UNSET이면 NULL. |
| 프로젝트 생성 기본값 | 실제 0원 예산 | 미설정. `[나중에 설정]`으로 온보딩 완료 가능. |

| 나중에 설정 | 0원에서 금액 변경 | 현재 전체 유효 지출로 계산, 기존 초과 안내와 향후 정책 적용. |

기존 v3.2의 권한 분리와 검토 반영 내용은 이어서 적용한다. 기존 50개 기능 ID를 유지하며 예산 미설정은 F-PROJ-02의 동작으로 정의했다. ERD·화면설계 파일은 이번 산출물의 수정 대상이 아니며, 적용할 최소 계약은 부록 B·C에 기록했다. 기존 데이터의 0원은 실제 0원으로 유지하고, 과거 0원이 미설정 의도였다고 추정해 NULL로 일괄 변환하지 않는다. 신규 프로젝트 기본값만 NULL로 변경하며 기존 프로젝트의 해제는 명시적 사용자 동작과 이력을 통해 처리한다.

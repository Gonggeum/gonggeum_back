# Flyway 마이그레이션

현재 마이그레이션은 다음 두 개다. ERD v1.3의 전체 36개 테이블 중 14개를 생성한다.

- `V1__create_identity_tables.sql`: 사용자·파일 메타데이터·약관·동의·세션·소셜·인증 자격·보안 설정·복구 코드·로그인 이력·알림 기본 설정 11개.
- `V2__create_request_and_cleanup_tables.sql`: 멱등 성공 기록·삭제 작업·삭제 작업 항목 3개.

사용자/프로필 파일의 순환 참조는 두 테이블을 만든 뒤 FK를 연결한다. 기존 데이터 삭제나 임의 약관/계정 seed는 없다. 약관 전문은 승인된 내용을 별도 게시해야 하며 테스트 fixture를 개발·운영 약관으로 사용하지 않는다.

`ddl-auto=validate`, `clean-disabled=true`를 유지한다. 지금은 읽기 API에 JdbcClient를 사용하고 JPA 엔티티 매핑은 아직 없으므로 Hibernate validate만으로 스키마가 검증되었다고 간주하지 않는다. MySQL 통합 테스트가 실제 UNIQUE/FK/CHECK/동시성 및 Flyway 재적용을 확인한다.

적용된 V1/V2는 수정하지 않고 다음 버전 파일로 변경한다. MySQL DDL은 전체 스크립트가 하나의 트랜잭션으로 롤백되지 않으므로 실패 시 현재 테이블과 Flyway 이력을 확인하고 후속 교정 절차를 작성한다. 개발 데이터가 있는 DB에서 clean 또는 테이블 재생성을 해결책으로 사용하지 않는다.

다음 가입 작업은 사용자·동의·기본 설정·세션·로그인 이력의 원자 저장을 구현한다. 감사 테이블은 팀/프로젝트 FK 대상과 함께 후속 마이그레이션으로 추가하되 첫 팀·프로젝트 쓰기 API 공개 전에 준비한다. 현재 멱등/삭제 테이블은 저장 구조이며 실행 서비스/워커는 미구현이다.
